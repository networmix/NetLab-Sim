# Protocol foundation contracts

This page states what the foundation for Open/R and BGP must guarantee. It
holds the common design decisions, the minimum contracts for the next slices
(F0 and F5) and the requirements that F1a, C6, S1a and S1b must meet. Later
slices keep their requirements in the archived design and are listed under
[Pending contracts](#pending-contracts). Nothing here is an available API: the
records, modules and names below are planned. Order and state are in
[docs/roadmap.md](../roadmap.md); how this page relates to the code and the archive
is in [the design index](README.md).

Two kinds of statement appear here:

- **Requirements** are what the implementation must do. Each slice's
  contract is complete only when its requirements are written as exact rules
  with their tests.
- **Vendor references** cite Open/R at commit `81dae4c` or FRR at master
  `f1d7bec` (10.8.0-dev; `10.5.4:` marks the SONiC release) by file and line.
  They record a source reading made for the archived design and have not been
  reproduced. A vendor behaviour becomes a guarantee only with a reproducer or
  a pinned fixture.

## Common decisions

These hold for every slice below and in the archived design.

- **References.** Open/R is followed module for module at `81dae4c`, including
  upstream facts that contradict common assumptions (no domain name;
  shortest-path ECMP only; a fresh node boots soft-drained; the default metric
  is RTT-based; area import policy is a stub). BGP follows the RFCs first and
  the modern FRR dialect where they leave room; `frr-10.5` (what SONiC builds)
  is a settings dialect. Generic version differences are settings with
  per-dialect defaults, never a version check in code, and vendor bugs are not
  emulated. FRR is GPL-2.0+, so its behaviour is reimplemented clean-room from
  RFCs, documentation and black-box runs; no code is copied. Anything
  NetLab-Sim adds beyond upstream Open/R is labelled as an extension and is off
  by default.
- **Differential oracle.** An optional lane runs pinned FRR images and compares
  converged state only; it is opt-in and outside the standard checks. Its
  goldens are committed as data generated by NetLab-Sim, and FRR test data is
  read from a pinned FRR checkout at run time, never vendored.
- **No privileged path.** Protocols are agents. They see only their agent
  context and act only through their output. They meet only through the RIB
  (route submission and the RIB feed), next-hop tracking (NHT) and views
  published on the same device. No agent reads another agent's state.
- **Structure mirrors the real implementation.** One package per protocol and
  one submodule per real module. A submodule is a pure function over frozen
  records and persistent maps, receives only the declared projection of the
  context it needs, and exchanges explicit queues with the others. A run drains
  the queues in a fixed priority order with a bound that raises when exceeded.
  Edges that wait for programming in reality wait for the owner notification
  of installation. Per-key deadlines go through one armed timer per module.
  Each module draws randomness from its own named stream.
- **Replaceable parts are named code, not an interpreter.** Decision flavors
  (`frr`, `rfc4271`, and classes a scenario adds at deployment) implement
  `compare`, `select` and `multipath` over narrow immutable inputs and are
  selected by a per-node setting. Callables never live in state or
  configuration. Every built-in rule declares its references (an RFC section,
  a vendor function or reason, or a document URL), and a test rejects a
  missing reference.
- **Domains are configuration.** A device runs 0..k IGP instances with
  disjoint interface sets (more than one instance is an extension, off by
  default) and at most one BGP instance. VRFs are deferred.
- **Cost proportional to change** is a performance exit criterion for every
  protocol slice: a one-prefix change costs the same at ten times the table
  size within a stated factor, and an idle run admits O(1) changed records and
  does no SPF, FIB or placement work. Large tables are persistent maps or
  packed tables, never tuples or frozensets. No unrelated-table scan for a
  local edit; affected closure, bulk configuration, SPF work and amortized
  compaction are budgeted explicitly. No Python object per route, path or FIB
  entry outside API boundaries, with one stated exception: the common
  submitted and admitted RIB at X may stay object-based if the memory ceiling
  is revised upward and stated ([S1b](#s1b-packedtable-and-its-index),
  Memory). No per-run tree write for identity outputs.
- **Timing.** Defaults are faithful to the reference profiles; a `lab` preset
  shortens timers but keeps the order of events. Protocol presets require a
  positive agent run delay, so feedback between agents on one device cannot run
  away within one timestamp.
- **Next hops follow FRR and zebra.** Single-hop eBGP registers NHT with
  `connected_only`, waits for that answer before connecting, and installs
  non-recursively. iBGP, confederation, multihop and GTSM eBGP install
  recursively through the resolver; BGP over BGP is allowed. The decision
  process uses the metric of the installed resolving route.
- **Keys are ready for add-path and VRFs**: paths keyed `(peer, path_id)`,
  destinations `(vrf, afi, safi, prefix)`, with `path_id = 0` and the default
  VRF until those features land.
- **No analytical BGP in this phase.** Import policy, decision and export stay
  pure, so a later timeless solver can reuse them.
- **Configuration is tree state; commands are exec-only.** Agent configuration
  changes in place within a generation and records a configuration cause;
  reset and fresh runtimes keep the latest configuration; plugins read
  configuration only from their context. Persistent agent state survives reset
  unless purged. Commands (clear, soft reset, route refresh, drain) are
  validated synchronously when submitted, report run-time errors in a view and
  are dropped and counted when their generation was reset first.
- **Restart semantics are explicit**: a purging reset models a plain daemon
  restart (zebra removes the client's routes); a retaining reset models Open/R's
  route retention until first sync and, later, BGP graceful restart.
- **Routing policy** is one typed engine in the model layer, shared by BGP,
  Open/R and the device hooks: [routing-policy](routing-policy.md).
- **Forwarding installation** is an asynchronous contract: desired and
  installed actions are separate, completions are generation-guarded, and FIB
  acknowledgement gating and inactive-route export are per-node behaviours.

## F0: contract additions

F0 adds records and fields only. Every addition has a default, so existing
agents, scenarios and results are unchanged. Its exit is a contract test for
every new record and rule, the existing suites unchanged, and the locality
rules extended to every new accessor.

**Freeze rule.** Records with no open obligation can land first. The listener,
recursive-resolution, programming, sync and packed-table records are frozen
only after the obligations of [S1a and S1b](#s1a-and-s1b-certificates-and-packed-tables),
[C6](#c6-zero-commit-publication), [F1a](#f1a-order-independent-resolver),
[programming, sync and feeds](#programming-sync-and-feeds), and routing
policy's [next-hop activation](routing-policy.md#next-hop-activation) and
[recursive next-hop keys](routing-policy.md#resolver-filtering) are expressed
in their fields. This page states those obligations; it does not fix field lists
or signatures.

### What F0 adds

- **Configuration, persistence, commands**: in-place agent configuration with
  a configuration cause; persistent agent state in the agent node and the agent
  output; a command record with its time, name, payload and target generation;
  a simulation entry point to submit commands; plugin hooks that validate a
  configuration and a command. Delivery is F2a.
- **Views**: agents publish immutable named views, stored in the agent node and
  compared by identity. Another agent on the same device reads them; a
  subscription can target one view key; the timeline records view changes;
  tests, timeline series and study stability predicates read views only.
- **RIB feed** (the analogue of zebra redistribution). A watch names a family,
  a set of source clients or all clients, and a kind. "All" excludes the
  owner's own client, and naming the own client is rejected.
  - Kind `selected` covers rows the resolver installed. It reports at the
    commit of a processed FIB epoch: upserts are the contributing routes of the
    changed entries, filtered to the watched sources, including installed
    prefixes whose contributing rows changed content only (metric or tag);
    removals are keys that left the set; nothing is reported while the FIB is
    pending.
  - Kind `all` covers every row of the watched sources whatever its selection,
    at the RIB commit of those rows.
  - A snapshot is delivered on registration and on every generation change.
    Feed entries are control-class inbox entries, coalesced as
    [programming, sync and feeds](#programming-sync-and-feeds) states.
- **Owner notifications**: for each changed own row, a `RowNotice` with the
  native status (`INSTALLED` or `NOT_INSTALLED`) and reason (`SHADOWED`,
  `UNRESOLVED`, `AMBIGUOUS_ACTION`, `LOOP_DETECTED`) plus the derived ZAPI code
  (`INSTALLED`, `FAIL_INSTALL`, `BETTER_ADMIN_WON`, `REMOVED`). A metric-only
  change counts.
- **NHT**: a mode per key, `rib` (today's answer) or `installed` (from the last
  processed FIB, as zebra answers), and an exact-prefix mode for BGP `network`
  import check (present exactly, resolved by a row that is not from BGP). The
  answer carries the metric of the selected first-level resolving row next to
  the strict cost. Notifications fire only on answer fields (`eligible`,
  `via_prefix`, `via_source`, `via_metric`, `cost`, `legs`), not on
  dependencies (`queries`, `interfaces`).
- **Change keys**: the NHT and row-notice change lists name the keys captured
  by this receipt: the union since the generation's previous published run,
  kept on rejection. Values are read from the snapshot; a key may have changed
  back. The initialization run receives empty lists and reconciles from the
  context.
- **Route views** separate the RIB-selected group at the input epoch (the
  desired projection) from the actual installed forwarding at the processed
  epoch. The desired row's installed projection may be absent while
  programming is pending; the actual installed content stays visible to
  forwarding and to installed-mode NHT until its replacement or deletion
  succeeds (see [programming, sync and feeds](#programming-sync-and-feeds)).
  Today one field reads the installed entry even while the row is pending.
- **Transport options**: wildcard listeners for a family scoped to an
  interface set; a per-listener accept table keyed by scoped remote identity
  with TTL and minimum TTL, refusing an unknown remote; TTL and minimum TTL on
  session open and a later option change; the connection view reports the
  concrete local endpoint. F3 implements them.
- **Lazy accessors** for own rows, one route, one row status and the RIB view,
  O(1) over immutable records, built from the detached local context and never
  from device state; no mutable cache.
- **Records F1 and F2 share**: resolver outcomes keyed by client, then row;
  NHT registrations held per owner; recursive next-hop and group records; a
  FIB group timeline event.
- **Packed-table records**: the record types whose obligations are under
  [S1b](#s1b-packedtable-and-its-index); S1b implements them.
- **Settings root**: a settings field on the network state and labels on
  devices, with the delta rules of [settings](#settings-delta-and-precedence).
- **Routing policy, programming and client profiles**: binding storage in
  settings, the route submission helper, the programming request, result,
  desired and installed action records and the `POLICY_EXCLUDED` reason, and
  node-local client-profile settings with the regression below.

### Per-node client profiles

A client profile (for example a route source's administrative distance) is
registered network-wide today. Two devices that run the same client with the
same profile are accepted; if one device uses distance 20 and the other 200,
the second registration is rejected because the client "is registered with a
different profile" (`netlab_sim/model/network.py`). Every protocol setting must
be overridable per node, so F0 adds node-local client-profile settings with a
regression test that fails on today's code: the same client with distance 20 on
node A and 200 on node B. No change of client identity may be used to work
around it.

### Programming, sync and feeds

These obligations bind the programming, sync and feed records that F0 defines
and X implements.

- **Route and group obligations.** Route requests and group requests have
  separate identities, desired and installed generations, and explicit
  dependency completion: a route becomes installed only when its group content
  is installed, and the previously installed action survives until then.
  Installed forwarding reads installed group content. An underlay change
  programs the group once and advances its installed version at completion;
  prefixes keep their group reference and are not re-requested. A group-only
  update avoids per-prefix programming only while selection and eligibility are
  unchanged; loss of eligibility triggers the budgeted re-election of affected
  prefixes (F1c). Supersession is resolved once, at the group obligation; an
  obsolete acknowledgement never satisfies a newer intent or releases a gate.
  Reclamation counts desired, installed and in-flight references; snapshots
  own their data. "Installed is absent while pending" is a projection of the
  desired row and never erases a retained installed action; installed content
  survives a pending or failed DELETE. Installed NHT and forwarding read
  installed content and its matching provenance. Pending, error and success
  are distinguishable from the first version: an explicit ERROR completion and
  a deterministic failure-injection seam.
- **Sync operations.** An accepted sync carries owner, generation and batch
  identity even when its RIB edit is the identity: an empty sync over an
  already-empty RIB, or a sync with no RIB delta, returns the same RIB today.
  (An empty full sync over an owner's existing rows withdraws them and is not
  an identity edit.) The programming boundary tracks the batch's upserts and
  deletions, including cleanup of retained installed routes, and emits one
  immutable completion with per-operation success and failure, or a distinct
  total failure. An empty batch completes successfully; failed removals are
  never omitted. Partial success reaches Open/R with the failed members
  scheduled for retry; total failure does not advance initial sync. Open/R
  publishes an empty full sync (vendor reference: `Fib.cpp:386-401, 849-859`),
  and its PrefixManager gate applies only to entries that carry next hops
  (`PrefixManager.cpp:650-662`). These records belong to F0 and X, not to the
  Open/R slices.
- **Route feed coalescing.** Feed messages identify their baseline and result
  epochs. Coalescing composes per-key final upserts and removals relative to the
  last captured baseline: disjoint edits are preserved and net no-ops cancel.
  At most one uncaptured entry exists per watch, and it is never merged into a
  captured or parked one. Registration and reset snapshots are distinct. Large
  snapshots and change sets use bounded pages or immutable table-backed views
  with declared byte limits and an explicit resync outcome; an entry count is
  not a memory bound.
- **Listener identity.** The accept table is keyed by scoped remote identity:
  family, address, and the ingress interface identity and generation where the
  address is link-local. That scope flows through connection lookup, accept
  options and collision identity. Listen ranges are a separate matching mode
  for globally scoped addresses.

### Settings delta and precedence

- The settings root is one of the root fields a state delta enumerates and is
  preserved by batches and forks; a settings-only update is never an empty
  delta. F0 owns this root integration; resolution and the per-owner action
  plan are F7a.
- Desired-layer edits and effective changes are tracked separately. An edit is
  preserved even when the effective value is equal; only effective changes
  schedule protocol work. Dumps serialize explicit values and inheritance
  intent, not only differences from dialect defaults. Tests: an
  equal-effective edit followed by a parent change; clear and unset; dump and
  load; aborted batch; fork; reset.
- Preset precedence: an explicitly inherited user instance value (for example
  100) beats a preset's neighbor value (200); only absent explicit inheritance
  falls back to presets. An explicit user profile (`datacenter`) beats a
  preset's profile (`traditional`); without a user profile the preset supplies
  it. Preset recursion and conflicting meta-key combinations are rejected.
- A configuration transaction resolves the complete candidate, diffs old and
  new effective records once, and compiles one plan per owner: reset or
  restart supersedes session work; recalculation, export and replay coalesce
  against the new revision; work deferred to the next session keeps its
  pending intent. Minimal provenance that explains each winning value ships
  with F7a.

## F5: protocol toolkit

Shared pieces both protocols use, so neither builds its own:

- **Selection**: the decision-flavor protocol (`compare`, `select`,
  `multipath`) with its narrow path, destination and context views, and small
  shared comparison helpers (AS_PATH length, MED comparability, router-id
  substitution), each with references. No interpreter and no hold or release
  slots.
- **SPF**: a pure ECMP Dijkstra over integer node ids returning distances,
  first hops and predecessor sets. Today the oracle IGP
  (`netlab_sim/model/igp.py`) and the reference agent
  (`netlab_sim/agents/reference.py`) each have their own; the toolkit gives
  protocols one.
- **Timers**: Open/R exponential backoff, async debounce, throttle, jitter
  drawn from a module's own stream of the agent's PRNG, and a per-module
  deadline structure that is one shared persistent priority structure with
  stated costs (arm and cancel O(log n), due O(k log n), stale entries
  bounded), never a tuple rebuilt per edit.
- **Route operations**: a RIB delta emitter keyed by changed-key sets.
- **Sizes**: modelled message sizes.
- **References**: a decorator that attaches an immutable reference tuple to rule
  functions, and one for tests that cover a reference.
- **Source address**: the primary address of the egress interface toward a
  destination, used by BGP when no update source is set.
- **Test harness**, one module for every protocol: the locality harness,
  guarded projection proxies (an undeclared read fails), twin comparisons with
  normalizers, and view-based assertions.

Exit: unit tests per helper and harness self-tests, including a projection
proxy rejecting an undeclared attribute read.

## F1a: order-independent resolver

Today the recursive resolver's answer for a prefix can depend on unrelated
routes and on the order in which prefixes are visited: depth is measured as
stack height, and results cut short by the stack or by the depth limit are
memoized. F1a makes each prefix's answer a function of the RIB only. It is the
one foundation slice that fixes a wrong result.

### Two separating examples

Both are reproduced on the baseline commit; their expected answers follow from
the rules below.

1. **A sibling cycle with an escape.** `eth1` is a numbered point-to-point
   link whose neighbour is `10.9.0.1`. Route A, `10.1.0.0/16`, has two next
   hops: out of `eth1` via `10.9.0.1`, and recursively via `10.2.0.1`. Route
   B, `10.2.0.0/16`, has one next hop, recursively via `10.1.0.1`. A's
   recursive leg leads through B back to A, so it closes a cycle and must fail
   with `LOOP_DETECTED`; A keeps its direct leg. B's leg resolves through A's
   direct leg, a finite witness that does not involve B. Expected: A and B
   both install out of `eth1` via `10.9.0.1`, in every visiting order. Today,
   resolving A first leaves B unresolved, and resolving B first installs
   both. Without A's recursive leg both install today.
2. **Unrelated routes change a chain's answer.** On the same link, recursive
   static routes Xi = `10.0.0.i/32` via `10.0.0.(i+1)` for i = 1..9, and X10
   = `10.0.0.10/32` out of `eth1` via `10.9.0.1`, with the default maximum recursion
   depth of 8. X5..X10 depend only on X6..X10. Expected: their
   answers are the same whether X1..X4 exist or not. Today they all resolve
   without X1..X4, and X5..X8 become unresolved when X1..X4, which no other
   route uses, are added.

### Rules

- Fingerprints come first: before the resolver changes, the fingerprint oracle
  (`tests/test_fingerprints.py`) covers outcomes (status and reason), MAC,
  encapsulation, adjacency family, NHT answers, selection and pending state,
  with recursive, cyclic, cross-family (RFC 8950), `lpm_fallthrough`,
  `resolve_via_default` and SR scenarios. Baselines are recorded and F1a's
  intended differences listed.
- Depth is the length of the next-hop chain, kept per recursive entry, not
  stack height. A depth-truncated result is never memoized. A prefix excludes
  only itself from its own resolution.
- **Per-leg witnesses.** A leg resolves when it has a finite resolution witness
  that does not support itself, with its candidate and exclusion context,
  within the depth bound; depth is checked per witness, not by one number per
  record. A leg whose only witnesses close a cycle fails with `LOOP_DETECTED`;
  cyclic branches contribute no weight unless an explicitly permitted acyclic
  escape exists. The route's other legs are unaffected, and weights are
  normalized over the surviving legs.
- Lower-ranked and less-specific fallback obey the selection and
  `lpm_fallthrough` rules; `all_or_nothing` is preserved; deduplication and
  weight combination are deterministic. A cached physical result is reused only
  where the exclusion context and the remaining depth cannot change the answer.
- The resolver's device context tests for an absent RIB by identity, not by
  truthiness (which measures the table on every prefix).

Tests fail on the old code and run under every enumeration order: closed
cycle; cycle plus a direct leg (example 1); cycle with two exits; unequal
branch depths; cycle plus a lower-ranked candidate; `all_or_nothing`; repeated
adjacency with unequal weights; blocked covering prefix and blocked
less-specific fallback; a chain with and without unrelated members (example
2); and a seeded fuzz of random RIBs in random prefix orders asserting identical
outcomes.

## C6: zero-commit publication

An agent run that changes nothing must publish nothing to the network tree,
while initialization, receipts and the PRNG stay exact.

### Current behaviour

An agent whose run returns the same state and no operations still replaces the
network root and adds a timeline record, because the per-run bookkeeping (`runs`,
`receipt`, `rng`) is stored in the agent node of the tree
(`netlab_sim/model/contracts.py`, `netlab_sim/runtime/agents.py`). This is
planned work, not a fault of the current API.

### Requirements

- **Publication seam.** A finalizer that runs no user code commits accepted
  runtime successors at the root publication point, before root observers, and
  performs the same transition on accepted batches with no root delta. A failed
  outer commit publishes neither side and keeps the retry captures. Captured
  prefixes are consumed before external callbacks. The pipeline distinguishes
  prepare, abort, publish and external finalization. The after-run hook alone is
  not the publication hook. Tests place an observer ahead of the runtime
  observers and inject an outer commit failure.
- **Initialization stays in the tree.** The node's initialized flag remains a
  one-time tree transition on a successful initialization run; only the per-run
  bookkeeping (`runs`, `receipt`, `rng`) leaves the tree. Fresh runtimes keep
  today's generation and reset semantics.
- **Runtime state.** Pre-run PRNG, counter and initialization state are captured
  in the per-generation journal and published at the same success boundary as
  the tree, including the no-delta case. Parked rejection and explicit retry
  are preserved. Reset, removal and generation purge clear every runtime map.
  Forking a network does not clone a running scheduler.
- **Receipts.** Current receipts come from an explicit simulation or agent
  runtime API as freshly frozen values, plus bounded history; bounded run events
  are emitted at runtime publication even without a root delta; an old snapshot
  never acquires a newer receipt.
- **PRNG.** The S0 generator keeps its contract: named and versioned with
  golden vectors, one counter per declared stream persisted across accepted
  runs and advanced only when drawn, stream keys from a fixed encoding hashed
  with BLAKE2b, every counter restored on a rejected run. The implementation is
  `netlab_sim/model/prng.py`; its design and evidence are in the
  [S0 W3 report](../history/s0-w3-prng.md).

Gate: every Gate C test, plus PRNG use in a no-delta run, mixed batches, a
failed outer commit and a callback failure after publication.

## S1a and S1b: certificates and packed tables

### S1a: changed-key certificate for `PMap`

- The persistent-map builder emits a certificate of changed and deleted keys,
  bound to the exact base map identity and result.
- Certificates compose across staged edits. Delete-then-reinsert and equal but
  different keys validate in full. An unrelated or rebuilt map falls back to full
  validation. The certificate is consumed on admission and never retains a
  parent chain.
- Generic immutability and semantic admission are distinct. Certificates are
  immutable evidence and never mutate a published map. An owner-local admission
  transaction composes edits back to the admitted base. A missing or mismatched
  certificate means full validation. The same lifecycle covers set, remove,
  update, build and the packed builder.
- The shard count stays 256 until a measured workload justifies another size.

### S1b: `PackedTable` and its index

- **Storage.** A persistent vector of fixed-width rows in immutable byte chunks,
  with a row layout per table kind. Admission treats the bytes as leaves, with
  no walk over rows. No published chunk is ever mutated; old snapshots keep old
  chunks.
- **Identity across compaction.** Positions are private to one table generation.
  External references are logical keys or `(table_generation, slot,
  slot_generation)` checked on dereference; a bare position never crosses a
  publication boundary (queued requests, dirty sets, back-indexes and
  completions carry logical identity or their snapshot).
- **First version is append-only**: no slot reuse or compaction within a live
  generation, an explicit memory limit, and rebuilding at a generation boundary
  as one owner transaction that publishes the table, every index, the pools and
  the allocator together with an explicit old-to-new remap. A rebuild is a
  storage change, never a route withdrawal. Bounded churn is not claimed for
  this version.
- **Builder.** Private and copy-on-write per chunk. Building freezes touched
  chunks and emits a change certificate of logical adds, updates and deletes,
  bound to the exact base and result generations and naming its coordinate
  system and any remap. Changed rows come from the builder's log, not from
  diffing chunks. The builder validates row schema, bounds and references.
  Attribute and peer ids are 32-bit and sequence numbers 64-bit; overflow is a
  validation error at the builder.
- **Index.** Small and full-table indexes implement the same exact lookup, LPM,
  exclusion and last-write-wins semantics. No packed sorted column is mandated.
  Bounded devices keep persistent per-length maps. Full-table devices adopt
  bounded sorted blocks of `(network_key, row_reference)` entries behind a
  persistent directory, with a defined 128-bit IPv6 ordering and family
  separation, only after their insertion, withdrawal, replacement, LPM and
  publication costs pass a benchmark under held snapshots. Numeric prefix ids
  are not address-order keys. A full per-length rebuild is a budgeted bulk
  operation, never a one-prefix edit.
- **Memory.** Per-row byte figures are hypotheses for named layouts. Reports
  state current, builder-peak, rebuild-peak and retained-history memory
  separately. The common submitted and admitted RIB with its indexes belongs to
  X; if it stays an object RIB, the memory ceiling is revised upward and stated.
  BGP's Loc-RIB uses stable path slots plus a bounded per-destination
  membership and order structure, never one monolithic compressed table.
  Scale passports name links, interfaces and local rows per device, and the
  protocol-churn passport fixes its workload (areas, degree, prefix
  distribution, timers) before it can pass.

Gate, before any protocol depends on it: held-snapshot tests across insert,
update, delete and rebuild; stale queued references; a remap failure rolling
back everything; admission; certificate and changed-row log correctness against
a brute-force logical diff; free-threaded readers on one snapshot; edit and
publication cost and retained-version memory measured.
